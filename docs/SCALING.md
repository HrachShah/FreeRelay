# FreeRelay Scaling Architecture

This document outlines the strategy for scaling FreeRelay to handle high request volumes and provide global low-latency inference.

## 1. Data Plane Scaling

### Regional Clusters
The Data Plane is designed to be stateless and can be deployed in multiple geographic regions (e.g., `us-east-1`, `eu-central-1`, `ap-southeast-1`).

- **Anycast Routing**: Use AWS Global Accelerator or Cloudflare to route client requests to the nearest healthy region.
- **Auto-scaling**: Deploy Data Plane workers as a containerized fleet (ECS/EKS/Railway) with CPU/Memory based auto-scaling.

### Shared State (Redis)
To support distributed rate limiting, circuit breaking, and caching, FreeRelay uses Redis.

- **Single Instance**: Default for development and low-volume production.
- **Redis Cluster**: Recommended for high availability and horizontal scaling of the state layer.
- **Global Replication**: For multi-region deployments, use a managed solution like **Upstash Global Database** to keep rate limits and circuit breaker states synchronized across regions with sub-millisecond replication.

## 2. Distributed Resilience

### Circuit Breaker Synchronization
Circuit breaker states are persisted in Redis. If a provider (e.g., Groq) starts failing in one region, the "OPEN" state is propagated to all regions, preventing redundant failures across the entire fleet.

### Rate Limiting
Rate limits are enforced globally per `user_id` or `org_id` using Redis Lua scripts for atomic sliding-window counters. This prevents "double-dipping" where a user could exceed their limit by hitting different regional endpoints.

## 3. Caching Strategy

### Semantic Cache
- **LSH Indexing**: Near-duplicate detection is performed locally on each node for performance.
- **Redis Storage**: The actual cached responses are stored in Redis with a TTL. This allows all nodes in a cluster to benefit from a cache hit generated by any node.

### Idempotency
- **Distributed Deduplication**: Idempotency keys (`X-Idempotency-Key`) are stored in Redis. This ensures that retries reaching different nodes are correctly deduplicated.

## 4. Control Plane Isolation
The Control Plane (Policy management, Learning engine) runs independently of the Data Plane.

- **Asynchronous Learning**: Outcome records are streamed to the Control Plane via Redis Pub/Sub or a message queue (SQS/Kafka).
- **Policy Distribution**: Updated routing policies are published to Redis, where Data Plane workers subscribe to real-time updates.

## 5. Managed Solutions Integration
For rapid scaling without infrastructure management:
- **State**: [Upstash Redis](https://upstash.com/) (Serverless, Global).
- **Database**: [Supabase](https://supabase.com/) (PostgreSQL + Auth).
- **Compute**: [Railway](https://railway.app/) or [Vercel](https://vercel.com/) (Serverless/Containerized).
